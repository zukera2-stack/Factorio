# EM072-A5-B7 — preflight: защита от изменяемого кэша и аудит реального потока EEI

## 1. Метаданные
- Дата: **2026-11-22**. Репозиторий: `zukera2-stack/Factorio`, база ветки `experiment/em072a5-native-brownout-b6` commit `80f41b04f1299071d263a228f9bf4fcc4779454d`. Ветка B7 только исследовательская.
- **Factorio Linux 2.1.24 build 87808**, Base, DLC отключены. Исходный игровой мод `ElectrifiedMainline 0.1.62`, **точный ZIP** из GitHub Actions [run 44925677432](https://github.com/zukera2-stack/Factorio/actions/runs/44925677432), SHA256 `91aef47ca13a0009e46ab92c9ad5735e0af30c6acc16bab1cf0507a8855a2575`.
- Предыдущий опыт B6: при 4×2MW тяги на втором участке план EM070 доходил до 20MW. Проверяется именно **исследовательская инъекция фиксированного спроса**, а не готовая модель тяги в продакшне.

## 2. Проверяемая операция
- Движок обновляет 2 нативных EM070, 16 живых составов (12+4), 84+84 заводских и 24+24 коридорных накопителя, 2 самостоятельных HSR-компонента. Скрипт запрашивает у `bridge_devices_060.sample` таблицу `direct` и добавляет спрос каждого независимого поезда.
- Угроза: `sample` кэширует **саму таблицу** на 60 тиков (`s.device_sample.data`); инъекция вида `direct[net].demand = old + train_j` может мутировать кэш, тем самым **накапливая заявку за несколько тиков**.
- Ожидаемое: 4×2MW = `133333.333333 J/tick` фиксированной лабораторной тяговой заявки, без повторного сложения за 60 тиков. Даже при нативном EEI-потребителе не прибавлять спрос дважды *между тиками*; `bridge_dispatch_059.balance` затем применяет `max(raw_demand, direct_demand)`.
- Не следует путать **`planned_mw`** (планировщик), **`M.transfer`** (скриптовый перенос только реально накопленной в нативном входном EEI энергии) и нативное сетевое потребление/накопление ванильных аккумуляторов.

## 3. Приёмочные сценарии и отрицательный контроль
1. Сохранить сценарий B6 без патча `direct` — ожидается воспроизведение 20MW и инкремента `direct_demand_J` каждые 5 тиков при неизменном `sampled_tick`.
2. **`copy_add`**: сначала полностью скопировать строки кэшированной таблицы `direct`, затем добавить собственную фиксированную заявку в копию **ровно один раз за тик**; исходный `s.device_sample.data` не мутировать.
3. **`copy_max`**: то же копирование и `max(существующее_значение, тяговая_заявка)`; проверить чувствительность к тому, что нативный EEI уже включён в измеренный спрос.
4. **`meter`**: исключить фиксированный дополнительный спрос на втором участке, наблюдать исключительно нативный EEI + `read_network`.
5. Сопоставить на тиках 250–295 `raw_secondary_demand`, `direct_demand`, заряд батареи, реальную энергию `M.transfer`, планы и фактически оплаченные Joules в четырёх нативных `LuaBurner`. Все накопители настоящие, изменение `accumulator.energy` во время хода теста запрещено.
6. Каждая версия: **500 настоящих тиков** на отдельном disposable мире; выбранный `copy_add`: серверное **SAVE t385 → независимый процесс LOAD +115 тиков**, полный конечный замкнутый J-ledger обоих участков.
7. Негативное условие: нет отличия 20MW и 0.8MW / растёт заявка в `copy_add` / необъяснённая энергия (abs residual >3J) / SAVE-LOAD расходится — FAIL.

## 5. Различия текущего кода и модели
- В оригинальном игровом `scripts/power_bridge_058.lua` **нет** B6 фиксированной инъекции 12+4 поездов. Это экспериментальный Lua-фрагмент, добавляемый исключительно в извлечённый CI ZIP в тестовой папке.
- В исходном моде `em-electric-locomotive` пока `void`-powered; B7 не доказывает готовый игровой электротяговый runtime и не должен менять его.
- `sample` считает network energy и EEI на временном снимке. При ссылочном изменении `direct` кэш `sample` перестаёт означать только данные приборов. Это противоречит принципу достоверного снимка.

## 6. Гипотеза и минимальная правка
- **Гипотеза:** восстановление иммутабельности `device_sample.data` путём копирования строк `direct` перед добавлением тестового спроса уберёт ложный 20MW план без снижения реального оплаченного движения поездов.
- Альтернативы: `max` с уже измеренным спросом и полностью native-meter-only. Они полезны для сравнительного опыта, но нельзя автоматически заменять суммирование для сети с иными сторонними потребителями: `max` мог бы потерять независимые нагрузки.
- Отмена: удалить disposable patch (одноразовая тестовая копия), всё остальное неизменно. Никакой миграции пользовательских сохранений.
- **Концептуальная граница:** после устранения ошибки остаётся выбор политики расходования **запаса коридорных аккумуляторов vs приоритета фабричной подачи**. Этот выбор не определяется техническим тестом; не изменять политику владельца без согласования.
