## I. Что действительно было проверено
1. **0.1.63/скриншоты владельца:** поезд движется, но потребление сети отсутствует. Исходник `prototypes/bootstrap.lua` явно ставит `em-electric-locomotive.energy_source={type="void"}` — безусловно не расходует сетевую энергию. Старые успешные мостовые EEI тесты подтверждали **перенос между сетями**, а не оплату движения.
2. **0.1.64:** дополнительный ordinary `em-electric-pole` исчез из рецептов и не выдаётся тестовой командой; его прототипы `item/entity/recipe` сохранены для старых сохранений; проверено [подлинным Factorio 2.1.24 run #45039543079](https://github.com/zukera2-stack/Factorio/actions/runs/45039543079). Это НЕ сам контактный столб 25 кВ и не доказательство тяги.
3. **0.1.65:** [native #45041147885](https://github.com/zukera2-stack/Factorio/actions/runs/45041147885) подтвердил **один** настоящий EM поезд, 20МВт источник типа native primary-output ElectricEnergyInterface, две подстанции, три мачты, 2МДж резерв, движение **24 клетки** до native AUTO станции без записи в `LuaTrain.speed`; получено 3.2МДж из native EM070 output и записано 3.2МДж в `LuaBurner.remaining_burning_fuel` (суммарные Lua счётчики). Сохранено на диск tick125 и перепроверено `--test-save` в отдельном процессе. Локомотив без сети в исходной проверке имел 0 Дж, но ему **не задавали маршрут**.
4. **Новая независимая проверка #45042971982** ([журнал](https://github.com/zukera2-stack/Factorio/actions/runs/45042971982/artifacts/14762317389)): две настоящие независимые EM машины на одном 25кВ участке, общая native EEI factory source **1МВт (16 666.667 Дж/тик)**, обе изначально 0 Дж и в итоге обе получили заряд. При tick60: A=933 333.333 Дж, B=0 Дж. Tick120 A=1 933 333.333 Дж, B=0 Дж. Tick240 A=1 983 333.333 Дж, B=1 950 000 Дж. Tick300 A=B=1 983 333.333 Дж. Обесточенный настоящий EM поезд с действительной native AUTO станцией на независимой карте остался **0 Дж и 0 клеток движения** до tick240 — отрицательный контроль действителен.
5. **Новая независимая проверка #45043138579** ([журнал](https://github.com/zukera2-stack/Factorio/actions/runs/45043138579/artifacts/14762098856)): все предыдущие результаты воспроизведены, плюс прямое измерение `mast.electric_network.parent_network.flow_last_tick` вместо синтетического `networks[id].load`. На tick60, tick120 и tick240: `native_primary_demand_J_tick = 0` и `native_secondary_demand_J_tick = 0`, когда заряд реальных двух локомотивов увеличивается до 0.933/1.933/3.933 МДж. На tick300 обе demand тоже нулевые, `native_secondary_output_J_tick=16666.667`. Генератор заводской сети реально измерен через native `primary_output=16666.667 Дж/тик`. Это **подтверждает ключевой остаточный дефект**: виртуальный планировщик EM070 потребление видит, а native 25кВ электрическая сеть не видит реальный поезд как нагрузку. Источник тестовый честный native EEI, не промышленный парогенератор.

## III. Что означают десять итераций
GitHub branch `experiment/em065-source-paid-locomotive-drive-native`: **22 Actions runs по 10 уникальным HEAD SHA**. Группы: docs 8 PASS/2 FAIL, full build 4 PASS/3 FAIL, native paid train 3 PASS/2 FAIL. Из десяти коммитов два реализовывали основную game runtime энергию (`05079b08` finite burner, `aa0ca5b2` EM070 virtual demand), один дописывал диагностику/тестовые гварды, один тестовый mock guard и native motion test; остальные — исследование, тестовые скрипты, исправления тестов, восстановление документов или отчёт. В частности, коммит `6c227ec8` удалил 2 414 строк проектных документов и сохранил зелёный отдельный native зарядный тест; только коммит `cf7e2535` восстановил их.

### Почему «PASS = всё работает» — ошибочная логика
- Отдельный PASS 20МВт native power bridge проверяет **передачу энергии в другие электрические сети**, а не поезд.
- `tests/test_full_mod_063.py` (5 статических проверок) читает версии/строки/prototype declarations, не проверяет физику, GUI, Undo, наполнение native Joules.
- Native 0.1.65 positive: 24 клетки на одной прямой; мощность 2МВт была заявлена в prototype `max_power="2MW"`, но реальные механические ватты, потребляемые при разгоне, не измерялись напрямую.
- В `scripts/traction_paid_065.lua` `stats.debited_J` и `stats.credited_J` оба увеличиваются одним и тем же `amount`; их равенство служит внутренней проверкой **одного алгоритмического переноса**, но само по себе не является независимой замкнутой бухгалтерией всех генераторов, буферов, накопителей и потерь. Старый 1.5МДж дефицит это особенно иллюстрирует.
- Первый нативный негатив `0J` не имел маршрута; улучшенный независимый тест с реальной станцией/авторежимом теперь PASS.
- Пользовательский обычный `em-electric-pole` скрыт корректно и недеструктивно; это отдельный визуально-каталожный ремонт, не исправление настоящей электросети.
- Наоборот, GREEN audit workflow #45043138579 означает «сценарий штатно отработал и оставил результат», а внутренний **`[AUDIT EM065 FAIRNESS DEFECT REPRODUCED]`** означает FEATURE FAIL. Значит статус действия не может заменить фактические assertions.

## IV. Порядок дальнейшей стабилизации
1. **P0 физическая нативная нагрузка:** экспериментальный native 25кВ consumer, реально соединённый с контактной сетью (без короткого замыкания заводской и контактной топологий). Переводить в двигатель только уже оплаченный потребителем native J, сравнить обе native flow-statistics и замкнутый баланс. Не устраивать второй источник энергии и не менять `LuaTrain.speed`.
2. **Справедливое ограничение источника:** отключить greedy заряд в `unit_number` FIFO при перегрузке. Распределять реально доступные Дж **до** записи в каждый burner, с явным ограничением суммарного входа и согласованной политикой (равные квоты, доли реальной тяговой потребности, приоритет безопасности). Новая native проба 1МВт/2 локомотива: обе машины получают >0 Дж одновременно при одинаковых запросах.
3. **Устранить orphan C5** прежде, чем подавать хоть сколько-то Дж на вагонные hidden helpers. Тесты owner destruction с true LOAD, Undo/Redo и двумя владельцами.
4. **Повторить строгий EM066 закрытый энергетический баланс** без подмены неучтённых потерь теоретическими дугами.
5. **Потом** полноценно внедрять 500кВт на каждый моторный вагон (без батарей), regen, и длинные маршруты: прямые, диагонали, дуги, развилки, высокие рельсы и HSR + Space Age.
6. **Клиентский gate:** владелец на отдельном Windows 11 тестовом SAVE видит GUI, статистику реальной нагрузки, старые предметы без слома инвентаря, миграцию 0.1.63, robot Blueprint/Undo, 60 UPS; допускается только после независимых нативных отрицательных тестов.
