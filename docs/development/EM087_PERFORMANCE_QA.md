## Цель и контракт

Никакого изменения мощности/законов тяги (2 МВт + 500 кВт/моторный вагон), лимита 20 МВт на подстанцию, энергетического баланса, геометрии, PNG, графики и native movement; не писать `train.speed`. Не ослаблять правила безопасности при обрыве/перестройке проводов. Технические локомотивы должны быть полностью невидимыми для игрока; ранее подтверждённые flags, запреты на GUI и blueprint сохраняются. Нативный GUI состава/станции ещё не проверен владельцем; не считать требование закрытым. Не менять main, принятые решения и файлы владельца.

## Изменения

Шесть игровых файлов (`info.json` и пять Lua). `traction_paid_065` перебирает native locomotive groups, а не carriages, использует минимальный подходящий ID подстанции без сортировки списка, один подтверждённый контакт на владельца внутри фазы выдачи и memo донора по network/force внутри одной фазы. Не переиспользует memo между bootstrap requests и paid settlement. Контакт возвращает проверенный anchor вместе с сетью. `helper_lifecycle_067` использует уже подсчитанное число вагонов внутри targets. `control` читает позиции один раз на поиск и повторно использует результат поиска рельса в одной визуальной/диагностической фазе.

Вторая итерация: `power_019` и `technical_network_046` используют локальную таблицу смежности рельсов и стартов обхода только на время одного синхронного M.plan. Сохранены порядок направлений и поворотов, критерии связности и силы/поверхности, стоимость и ограничения поиска, частота полного sync (600 тиков) и аудит (60 тиков). Не сохраняются ссылки на рельсы в storage и не кэшируется топология между тиками; в аудите повторно используется ссылка на один anchor. Вне планирования path_check без общего memo. Код профилирования только в отдельном исследовательском архиве, не в патче. 157 игровых файлов, 99/99 PNG прежние, ни одного удаления.

## Методика

Factorio Linux headless 2.1.24 build 87808. Синтетические сохранения реального движка, не пользовательские данные. Host report AMD EPYC 9V74, 5 видимых cores; cgroup cpu quota 4 CPU, память 4 GiB. Для длинного состава (201 моторный вагон) использовано синтетическое сохранение на 80-м тике 0.1.85 из EM085 аудита, одинаковые входные байты, 3 × 1200 тиков на вариант. Для масштаба 1/10/50/100: параллельные изолированные пути, по одному настоящему локомотиву, грузовому, жидкостному моторным вагонам и одной подстанции 20 МВт с синтетическим источником на поезд. Созданы сервером на 0.1.86, сохранены на 120-м тике, измерение 480 тиков до 600 включительно, 2 запуска для 1/10/50 и 1 для 100. Груз 37 пластин на состав, неподвижные насыщенные буферы. Не моделирует постоянно движущиеся 100 поездов или большую обычную фабрику. Размеры логов/нагрузка окружения и конфигурационная перестройка при смене версии влияют на измерения; малая выборка, не статистическая гарантия. Сначала R1 (поезда), потом R2 (топология). R1 логи отдельно. Все данные в logs/ и benchmarks.json.

Первый массовый тест ошибочно проверял helper на тике 0 — ошибка стенда, исправлено на тик >=120, исходный мод не тронут. Серверное сохранение 800 прервалось внешним ограничением запуска; отдельный native тест ниже успешен.

EM087 PARTIAL; не переходить к аккумулятору EM088, пока не установлен приёмочный порог оптимизации. Следующий эксперимент EM087B: профилировать bridge058 в постоянной работе 1/10/50/100 движущихся поездов; сократить повторный `network_key`, `sole_link`, обращения к нативным объектам только с доказанным контрактом; разработать инкрементальный технический граф с событиями рельсов/мачт и периодическим независимым аудитом, проверкой split/rejoin, несвязанными путями, кривыми, вилками, force/surface, SAVE/LOAD, без устаревшего разрешения тяги. Проверить, возможно ли безопасно ограничить работу тяжёлого полного пересчёта на один тик, не отключая аудит и не разрешая бесплатную тягу. Не маскировать проблему уменьшением частоты проверок или выключением диагностики. Цель: запас от 16.667 ms на весь тик, без крупных периодических зависаний; отдельно метрики p95/p99, память, движение 100 поездов, длинная линия и реальные карты.
